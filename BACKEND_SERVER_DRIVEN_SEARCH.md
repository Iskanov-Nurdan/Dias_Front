# Server-driven search: что должен поддерживать бэкенд

Фронт переходит на схему «только ответ сервера»: поиск/фильтрация только на бэкенде. Сейчас фронт будет слать перечисленные ниже query-параметры; нужно, чтобы эндпоинты их принимали и возвращали уже отфильтрованный список.

## Эндпоинты и параметры

| Метод и путь | Новый/используемый параметр | Назначение |
|--------------|-----------------------------|------------|
| **GET /api/roles/** | `search` | Поиск по названию роли (подстрока, без учёта регистра). |
| **GET /api/sports/** | `search` | Поиск по названию вида спорта (подстрока). |
| **GET /api/trainers/** | `search` | Поиск по ФИО тренера (подстрока). Уже есть: sportId, page, perPage. |
| **GET /api/warehouse/categories/** | `search` | Поиск по названию категории (подстрока). |
| **GET /api/warehouse/products/** | Уже есть `search` | Без изменений. |
| **GET /api/warehouse/restocks/** (история пополнений) | `search` | Поиск по названию товара (подстрока). |
| **GET /api/expense-categories/** | `search` | Поиск по названию категории расхода (подстрока). |
| **GET /api/expenses/** | `search` | Поиск по названию расхода, категории, сумме или дате (подстрока/совпадение). Уже есть: dateFrom, dateTo, categoryId, page, perPage. |

## Формат

- Имена параметров в camelCase: `search`, `categoryId`, `sportId`, `dateFrom`, `dateTo`, `page`, `perPage`.
- Если параметр не передан или пустой — возвращать список без фильтра по этому полю (как сейчас).
- Ответ: как сейчас (items/results + при необходимости meta/links для пагинации). Менять формат ответа не требуется.

Фронт уже передаёт эти параметры в запросах и рендерит только ответ сервера (без локальной фильтрации по поиску).
