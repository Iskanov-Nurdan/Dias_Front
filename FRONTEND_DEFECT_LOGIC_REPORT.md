# Отчёт: брак на складе и в продаже (good / defect)

## Что изменено

### Страницы

- **Склад** (`WarehousePage.jsx`, `WarehousePage.scss`): колонка «Качество» (бейджи Годный / Брак), фильтр «Все / Годные / Брак» (query `quality` + дублирующая клиентская фильтрация по полям партии), краткая строка причины брака под продуктом, строка таблицы с классом `data-table__row--warehouse-defect`, в модалке резерва — напоминание для партии брака.
- **Продажи** (`SalesPage.jsx`, `SalesPage.scss`): в списке продаж у строки с партией брака — бейдж «Брак»; в модалке продажи — префикс «Брак ·» в списке партий, баннер склада с акцентом для брака и текстом причины (если есть).
- **ОТК** (`OTKPage.jsx`, `OTKPage.scss`): подсказка под заголовком формы приёмки о поступлении годного и брака на склад отдельными партиями; подписи фильтра истории «Годный» / «Брак» вместо формулировок про «забраковано» как исчезновение.

### Таблицы

- Склад: порядок колонок — Статус, Качество, Продукт (+ причина брака при наличии), Количество, Партия, действия; мобильные подписи колонок обновлены.
- Продажи: ячейка «Профиль / партия» разбита на блок с заголовком, бейджом брака и номером партии.

### Модалки

- **Упаковка** (`PackFromOtkModal.jsx`, стили в `WarehousePage.scss`): выбор **конкретной партии** склада (не продукта + ручной ввод размеров); read-only блок с качеством, причиной брака (если есть), строкой «Высота × ширина × угол» с данных партии; поля «Упаковок», «Штук в каждой»; опциональный комментарий; `POST warehouse/batches/package/` с `warehouse_batch_id` / `warehouse_batch`, `pieces_per_package`, `packages_count`, опционально `comment`.
- **Резерв** (в `WarehousePage.jsx`): для брака показывается бейдж и причина.
- **Детали партии** (`warehouseBatchCard.js`): в начале списка полей — «Качество», при наличии — «Причина брака»; подпись источника уточнена как «Источник (ProductionBatch)».

### Формы

- Упаковка: убраны поля ввода высоты, ширины, угла; добавлен выбор партии и комментарий.
- Склад: в query списка добавлен параметр `quality` (пусто / `good` / `defect`).

### Общая логика и подписи

- **`warehouseQuality.js`**: качество только из поля `quality` (`good` | `defect`); причина брака — только `defect_reason` (`readWarehouseDefectReason`).
- **`erpLabels.js`**: подписи итогов ОТК в истории — «Годный → склад», «Годн. + брак → склад», «Брак → склад» вместо «Забраковано» без привязки к складу.

### API (комментарии)

- `warehouseApi.js`: описание тела `package/` обновлено под выбор партии.
- `productionApi.js`: комментарий к `submit-for-otk` сокращён (без намёка на списание только).

## Как теперь отображается брак

- **Склад**: бейдж «Брак» / «Годный», строка с лёгким фоном для партии брака, под продуктом — укороченная причина; в карточке деталей — полные поля качества, причины, источника, параметров.
- **Детали**: через `buildWarehouseBatchCardRows` — качество и причина вверху списка.
- **Продажа**: в выпадающем списке партий брак помечен префиксом «Брак ·»; после выбора — баннер с бейджом и полной причиной; в таблице продаж — бейдж «Брак» для строк, где качество определяется из `warehouse_batch` или плоских полей ответа.

---

## Что убрано

- Из формы **упаковки**: поля «Высота, м», «Ширина, м», «Угол, °» и логика `sumNotPackedQtyMatchingParams` по ручному вводу размеров.
- Из тела запроса упаковки (на фронте): `product_id`, `shift_height`, `shift_width`, `angle_deg`, `unit_meters`, `package_total_meters`, `width_meters` — вместо них идентификатор выбранной складской партии (дублируются ключи `warehouse_batch_id` и `warehouse_batch` для совместимости с DRF).

Тексты ОТК / фильтра истории, создававшие ощущение, что «забраковано» = исчезло, заменены на формулировки со **складом**.

---

## Что проверить вручную

1. Список склада: у партий с `quality=defect` (или эквивалентом с бэка) виден бейдж «Брак», фильтр «Брак» показывает только их.
2. Фильтр «Годные» и пустой фильтр «Все».
3. У партии брака с заполненным `defect_reason` / `otk_defect_reason` — строка в таблице и блок в деталях.
4. Упаковка: выбор неупакованной партии (годной и брака), без ввода размеров; успешный `POST` на бэке с новым контрактом.
5. Продажа: в списке доступных партий есть брак; оформление продажи с партией брака; бейдж и причина в модалке.
6. ОТК: после сохранения приёмки на складе появляются две партии при смешанном результате (проверка на стороне API/данных).
7. История ОТК: статусы в таблице читаются как переход на склад (подписи из `otkResultStatusRu`).
8. Резерв доступной партии брака (если бизнес-правило на бэке разрешает `status=available` для defect).

---

*Качество на бэке — только ключ `quality`: `good` или `defect`.*
