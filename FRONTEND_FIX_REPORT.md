# FRONTEND_FIX_REPORT

Отчёт о правках фронтенда под единую производственную модель: **факт производства = ProductionBatch**, цепочка **Сырьё → Химия → Рецепт → ProductionBatch → ОТК → Склад ГП → Продажи**.

---

# Что было не так

- В текстах и комментариях фигурировал **RecipeRun** / «замес» как отдельная сущность производства (`ProductionPage`, `linesApi`, `otkApi`, realtime refetch `recipe_run`, кнопка «Партия профиля» на линиях), что расходилось с правилом «единственный центр — ProductionBatch».
- Запрос линий для модалки партии использовал только имя query **`eligible_for_recipe_run`**, что в UX и в контракте выглядело как привязка к RecipeRun, а не к партии.
- В **производстве** заголовки колонок себестоимости были «₽/м», «₽/шт», при этом в других модулях используются сомы — визуально противоречие и путаница.
- В **деталях партии** валюта отображалась как «₽», заголовок модалки не подчёркивал тип сущности.
- **Рецепты**: при отсутствии профилей можно было открыть «Добавить рецепт» и упереться в пустой выбор профиля; в составе подписи компонентов `[Сырьё]`/`[Химия]` менее явно читались как один список «сырьё или химия».
- **Модалка новой партии**: порядок полей начинался с линии; не было явного блока при нуле профилей; подсказка не формулировала роль ProductionBatch как единственного места списания/метража/себестоимости.
- **ОТК**: realtime подписывался на `recipe_run`; подсказки по рецепту могли восприниматься как отдельный «источник» нормы выпуска вместо справки к партии.
- **Склад ГП и продажи**: не было короткого пояснения цепочки относительно ProductionBatch; модалка продажи не дублировала правило «только со склада».
- В **`erpLabels.js`** были экспорты `productionRunStatusRu` / `recipeRunListStatusRu` с терминологией замеса — не использовались в коде, но поддерживали устаревшую лексику в публичном API пакета `shared/lib`.
- В **`recipeRelease.js`** комментарии отсылали к recipe-run и «замесу» как к источнику количества для UI.

# Как теперь выглядит правильный пользовательский сценарий

1. **Профиль** — в разделе «Профили» создаётся конечный вид продукции; без профиля рецепт и партия недоступны (баннер и блокировки на странице рецептов и в модалке партии).
2. **Рецепт** — в «Рецептах» (или переход из профиля): только норма на 1 м, состав через **один** список «Сырьё: …» / «Химия: …»; явно указано, что списание не здесь.
3. **Производство** — «Новая партия»: профиль → рецепт этого профиля → линия из списка с открытой сменой (query-фильтр под партии) → штуки и длина; метраж и себестоимость не вводятся; подсказка про ProductionBatch.
4. **ОТК** — проверка **партии ProductionBatch**; в форме напоминание про сумму принято+брак относительно штук партии (логика валидации как была при известном выпуске).
5. **Склад ГП** — текст сверху: приём после производства и ОТК; не позиционируется как источник производства.
6. **Продажи** — выбор только партий склада ГП; lede и модалка подчёркивают цепочку через производство и ОТК.

---

# Как теперь отображается роль RecipeRun

- **Отдельного экрана или сущности RecipeRun в UI нет.**
- Имя query **`eligible_for_recipe_run`** оставлено **только** в объекте `LINES_QUERY_OPEN_SHIFT_FOR_PRODUCTION_BATCH` рядом с **`eligible_for_production_batch`** для совместимости с бэкендом на период миграции; в пользовательских текстах и в основном описании UI это не выносится как «RecipeRun».
- Realtime-обработчик **больше не подписан на `recipe_run`** (если бэкенд продолжит слать только это имя события, обновление ОТК по WS может не сработать — см. раздел проверки вручную).
- В **аналитике** по-прежнему может отображаться поле ответа вроде `recipe_run_label` в детализации списаний — это данные бэка, не отдельный сценарий UI; отдельной логики под RecipeRun не добавлялось.

# Что проверить вручную

1. **GET `lines/`** с параметрами `eligible_for_production_batch=true` и `eligible_for_recipe_run=true`: убедиться, что бэкенд не отвечает 400 и что список линий в модалке партии не пустой при открытой смене (если один из параметров лишний на вашей версии API — убрать лишний в `LINES_QUERY_OPEN_SHIFT_FOR_PRODUCTION_BATCH`).
2. **WebSocket `change`**: если ресурс называется иначе, чем `production_batch` / `batch` / `warehouse_batch`, проверить обновление списков ОТК и склада после событий.
3. Создание **профиля → рецепта → партии** с нуля; попытка «Добавить рецепт» без профилей — баннер и disabled.
4. **Новая партия** без открытой смены — сообщение об ошибке; с открытой — успешный POST `batches/`.
5. **ОТК**: при известном количестве к проверке — принято+брак равно выпуску; сохранение `otk_accept/`.
6. **Склад**: резерв и упаковка после появления партий на складе.
7. **Продажа**: только с `warehouse/batches/?status=available`; создание и накладная.

# Что не удалось полностью устранить в коде

- **Имя query `eligible_for_recipe_run`** технически остаётся в запросе (наряду с `eligible_for_production_batch`) до полной смены контракта на бэкенде — иначе возможен регресс на старых развёртываниях.
- Полное удаление любых полей ответа бэка с текстом «recipe run» из всех экранов **не делалось** (например, аналитика) — затронуты только управляемые тексты и подписки фронта.
