# API: график работы тренеров

Документ для бэкенда. Фронтенд уже вызывает эти контракты (`src/features/sports-trainers/api.js`).

## Соглашения

- **День недели `weekday`:** целое число **1 = понедельник … 7 = воскресенье** (как в ISO 8601).
- **Время:** строки **`HH:mm`** в 24-часовом формате (локаль зала — на усмотрение сервера, главное — единообразие).
- **Интервалы:** полуинтервал **`[start, end)`** — начало включительно, конец не включительно (как у слотов). Если бэкенд хочет включать конец — зафиксируйте это в ответе и согласуйте с фронтом.

---

## 1. График одного тренера

### `GET /api/trainers/{id}/schedule/`

Возвращает график тренера с идентификатором `id`.

**Успех 200** — пример тела:

```json
{
  "weekdays": [
    {
      "weekday": 1,
      "enabled": true,
      "intervals": [
        { "start": "12:00", "end": "14:00" },
        { "start": "16:00", "end": "18:00" }
      ]
    },
    {
      "weekday": 2,
      "enabled": false,
      "intervals": []
    }
  ]
}
```

Допустимы синонимы полей для совместимости (фронт при разборе ответа может не использовать их, но полезно поддержать):

| Канонически | Альтернатива (snake_case) |
|-------------|---------------------------|
| `weekdays`  | `week_days`               |
| `intervals` | `time_slots`              |

Если графика ещё нет, удобно ответить **200** с пустым списком или семью днями с `enabled: false` и `intervals: []`. Допустим и **404** — фронт трактует как «пустой график».

### `PUT /api/trainers/{id}/schedule/`

Полная замена графика. Тело в том же формате, что и в ответе `GET` (достаточно передать только дни с `enabled: true` и непустыми `intervals`, либо полный массив из 7 дней — на усмотрение реализации).

**Валидация (рекомендуется):**

- для каждого дня с `enabled: true` — хотя бы один интервал с непустыми `start` и `end`;
- `start < end` для каждого интервала;
- при необходимости — запрет пересечений интервалов внутри одного дня.

**Успех 200/204** — график сохранён. Тело ответа может повторять сохранённый объект или быть пустым.

**Ошибки:** 400 (валидация), 403 (нет прав), 404 (тренер не найден).

## 2. Список тренеров с фильтром по графику

### `GET /api/trainers/`

К существующим параметрам (`sportId` / `sport_id`, `search`, `page`, `perPage`, …) добавить **опциональные** query-параметры:

| Параметр (camelCase) | Альтернатива (snake_case) | Описание |
|----------------------|---------------------------|----------|
| `weekday`            | `week_day`                | День недели 1–7 |
| `timeFrom`           | `time_from`               | Начало диапазона `HH:mm` |
| `timeTo`             | `time_to`                 | Конец диапазона `HH:mm` |

**Семантика фильтра:**

- Если передан только **`weekday`**: в выборку попадают тренеры, у которых в этот день есть **хотя бы один** интервал с ненулевой длительностью (`enabled` / наличие интервалов — по вашей модели).
- Если переданы **`timeFrom`** и/или **`timeTo`** **без** `weekday` (форма клиента так устроена): тренер подходит, если в **любой** день недели есть интервал, удовлетворяющий времени (точка «с», диапазон «с–до» или пересечение — по той же логике, что ниже).
- Если переданы и **`weekday`**, и время: интервал должен быть в **этот** день и удовлетворять времени.
- Если передан только один из `timeFrom` / `timeTo` — поведение: либо игнорировать оба, либо трактовать как точку времени; фронт в карточке клиента может передать только «с», только «до» или оба.

**Опционально:** включать в каждый элемент списка тренеров вложенный объект **`schedule`** (тот же формат, что `GET .../schedule/`), чтобы клиент мог дополнительно фильтровать на фронте при необходимости.

## 3. Клиент: день и время занятий

При создании/обновлении клиента (`POST/PATCH /api/clients/`) фронт может передавать поля (camelCase в JSON):

| Поле | Альтернатива (snake_case) | Тип | Описание |
|------|---------------------------|-----|----------|
| `trainingWeekday` | `training_weekday` | integer 1–7 | Опционально; в форме добавления клиента **не задаётся**, может приходить из других каналов или старых записей |
| `trainingTimeFrom` | `training_time_from` | string `HH:mm` | Начало предпочтительного окна занятия |
| `trainingTimeTo` | `training_time_to` | string `HH:mm` | Конец предпочтительного окна занятия |

Поля **необязательны**. Фронт при создании/редактировании клиента передаёт в основном пару **`trainingTimeFrom` / `trainingTimeTo`** (время занятия без привязки к дню недели в UI).

При отдаче клиента в `GET /api/clients/{id}/` и в списках желательно возвращать те же поля, чтобы форма редактирования подставляла значения.

---

## 4. Права доступа

- Настройка графика (`PUT .../schedule/`) — как минимум роль администратора (как у редактирования тренера).
- Просмотр графика (`GET .../schedule/`) — все пользователи, которым доступен раздел тренеров/клиентов, если это соответствует вашей модели.

---

## 5. Чек-лист для бэкенда

1. Таблица или JSON-поле «расписание по дням» у сущности **Trainer**, связь один-к-одному с тренером.
2. Эндпоинты `GET` + `PUT` `/api/trainers/{id}/schedule/`.
3. Расширение `GET /api/trainers/` фильтрами `weekday`, `timeFrom`, `timeTo` (и snake_case дубликатами в query).
4. Поля `training_weekday`, `training_time_from`, `training_time_to` у **Client** (миграция + сериализация).
5. (Опционально) Вложенный `schedule` в элементах списка `GET /api/trainers/`.

После этого фронт заработает без доработок или с минимальными правками под фактический формат ошибок валидации.
