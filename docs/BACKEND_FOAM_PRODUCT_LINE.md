# Бэкенд: вторая продуктовая линия — Пенополистирол (пенопласт)

Фронт (`Dias_Front`) уже содержит полностью рабочий **визуальный прототип** второй линии
на моках (`src/features/foam/mockData.js`, `src/features/foam/store.js`) — без единого
обращения к API. Этот документ описывает, что нужно от бэкенда, чтобы заменить моки на
реальные данные, ничего не сломав в существующей линии «Пластиковый профиль».

## 0. Общая идея

- Появляется **второй склад сырья** и **вторая линия производства**, физически не связанная
  с пластиковым профилем (другое сырьё, другой процесс, другой склад ГП).
- В UI это **не новые пункты меню** — на страницах «Сырьё», «Производство», «Склад», «Касса → Продажи»
  сверху добавлен переключатель **«Пластиковый профиль» / «Пенополистирол»** (компонент
  `ProductLineTabs`, состояние — `localStorage`, чисто фронтовое). Бэкенду отдельные `access_key`
  под линию заводить **не нужно** — права те же, что и сейчас (`materials`, `production`,
  `warehouse`, `sales`). Открытый вопрос — см. п.7.
- **ОТК для этой линии не нужен вообще.** Реальный процесс: гранула → производство → готовая
  продукция сразу на склад. Никакой приёмки/проверки/брака на отдельном этапе — подтверждено
  заказчиком отдельно после того, как мы сначала сделали ОТК-этап и убрали его по его просьбе.
  На странице «ОТК» линия пенопласта не показывается вообще.
- Реальный техпроцесс (то, что должна знать бизнес-логика):
  1. Сырьё — гранула вспенивающегося полистирола (биг-бэги), поступает от поставщика.
  2. Производство берёт кг гранулы и с потерей 3.5% выдаёт **либо** «Куб» (спечённый блок
     фиксированного размера 60×100×200 см = 1.2 м³, вес зависит от выбранной плотности),
     **либо** «Гранулы на продажу» (обработанная гранула россыпью, на развес, без плотности).
  3. Готовая продукция сразу на склад ГП (без промежуточного контроля качества).
  4. «Лист» — не производственный формат: на складе куб можно нарезать на листы нужной
     толщины (2/3/4 см), листы кроятся из тех же 60 см высоты куба.
  5. Касса продаёт клиенту любую строку остатка склада ГП (куб/лист/гранулы).

## 1. Сырьё — лоты гранулы + справочник плотностей

### 1.1 Лоты (приход сырья)

```
GET  /api/foam/raw-lots/
POST /api/foam/raw-lots/
```

Поля лота:

| Поле | Тип | Описание |
|---|---|---|
| `id` | int | |
| `lot_number` | string | Генерируется бэком автоматически (напр. `KG-260804-001`), **не вводится пользователем** — см. п.7 |
| `material_name` | string, обязательное | Название сырья, вводит пользователь (напр. «Гранула EPS Kingeps HS») |
| `supplier` | string | Поставщик |
| `received_kg` | decimal | Вес прихода |
| `remaining_kg` | decimal | Остаток (уменьшается при запуске производства) |
| `received_at` | datetime | |
| `status` | enum | `in_stock` / `low` (≤15% от `received_kg`) / `empty` (0) — можно считать на фронте, но проще отдавать готовым полем |

`POST` body:

```json
{ "material_name": "Гранула EPS Kingeps HS", "supplier": "Kingeps", "received_kg": "800" }
```

**Важно:** у лота сырья **нет** плотности и **нет** поля «вес мешка/упаковки» — это было в
ранней версии прототипа и осознанно убрано. Плотность выбирается позже, на производстве,
и только для формата «Куб».

### 1.2 Справочник плотностей

```
GET  /api/foam/density-grades/
POST /api/foam/density-grades/
```

| Поле | Тип |
|---|---|
| `code` | string, уникальный (напр. `"12"`, `"14-15"` — свои заводские обозначения, не ГОСТ-марки) |
| `min_kg_m3` | decimal |
| `max_kg_m3` | decimal, ≥ `min_kg_m3` |

Средняя плотность = `(min_kg_m3 + max_kg_m3) / 2` — используется в расчётах производства (п.3).

### 1.3 Движения сырья

```
GET /api/foam/materials/movements/
```

Объединённая лента: приход (из лотов) + списание в производство (из партий производства).
Можно не делать отдельной таблицей — фронт сейчас просто мержит `raw-lots` (приход) и
`production-runs` (расход, поле `input_kg`) по дате. На бэке ок либо так же вычислять на лету,
либо завести отдельный лог движений — на усмотрение бэка.

## 2. Производство

```
GET  /api/foam/production-runs/
POST /api/foam/production-runs/
```

`POST` body:

```json
{
  "lot_id": 12,
  "input_kg": "150",
  "output_format": "cube",
  "grade_code": "12"
}
```

- `output_format`: `"cube"` | `"granule"`.
- `grade_code` — **обязателен** при `output_format = "cube"`, **должен отсутствовать/игнорироваться**
  при `"granule"` (у гранул на продажу плотности нет — валидировать явно, не просто игнорировать).
- `output_qty` **не передаётся фронтом** — бэк считает сам по формулам из п.6, возвращает в ответе.

Что должен сделать бэк при создании партии:

1. Провалидировать `input_kg ≤ lot.remaining_kg`.
2. Посчитать `output_qty` по формулам п.6.
3. Списать `input_kg` с `raw_lot.remaining_kg`.
4. **Сразу** (без ОТК) прибавить `output_qty` к соответствующей строке остатка склада ГП
   (см. п.4) — если строки с таким форматом+плотностью ещё нет, создать.
5. Записать операцию склада `kind = production_intake` (см. п.4.2).
6. Вернуть партию с посчитанным `output_qty`.

Поля партии в ответе:

| Поле | Тип |
|---|---|
| `id` | int |
| `lot_id`, `lot_number`, `material_name` | из лота-источника |
| `grade_code` | только для `cube` |
| `input_kg` | как передал фронт |
| `output_format`, `output_qty` | посчитано бэком |
| `produced_at` | datetime |
| `operator` | string — имя текущего пользователя (`user.name`/`role_name`), фронт передаёт сам |

Партии производства **не отменяются и не редактируются** — если ввели неправильно, это
компенсируется через операции склада (брак/возврат) или ручную корректировку, отдельного
API для «отмены партии» не нужно (было в раннем прототипе вместе с ОТК, убрано вместе с ним).

## 3. Склад готовой продукции (ГП)

### 3.1 Остатки

```
GET /api/foam/gp-stock/
```

Агрегированные строки остатка — **одна строка на комбинацию** формат+плотность(+толщина
для листа):

| Поле | Тип |
|---|---|
| `key` | string — стабильный ключ строки, напр. `granule`, `cube-12`, `sheet-12-3` (или обычный `id`, на усмотрение бэка) |
| `output_format` | `cube` \| `sheet` \| `granule` |
| `grade_code` | для `cube`/`sheet` |
| `thickness_cm` | только для `sheet` |
| `qty` | остаток: шт (куб/лист) или кг (гранулы) |
| `warehouse` | `"Склад ГП — Пенопласт"` |

Вес остатка (кг) фронт считает сам по формулам п.6 (`unit_weight_kg × qty`) — можно отдавать
уже готовым полем `weight_kg`, если бэку так удобнее, дублирования не будет, фронт возьмёт
что есть.

### 3.2 Нарезка куба на листы

```
POST /api/foam/gp-stock/cut/
```

```json
{ "grade_code": "12", "thickness_cm": 3, "cubes_qty": "2" }
```

- Списывает `cubes_qty` со строки `cube-{grade_code}` (400 если не хватает).
- Листов из одного куба = `floor(60 / thickness_cm)` (высота куба фиксирована — 60 см).
- Прибавляет `floor(листов_из_куба × cubes_qty)` к строке `sheet-{grade_code}-{thickness_cm}`
  (создать, если нет).
- Пишет 2 операции склада: `cut_in` (+листы) и `cut_out` (−кубы).

### 3.3 История движений склада

```
GET /api/foam/gp-operations/
```

| Поле | Тип |
|---|---|
| `id`, `created_at` | |
| `kind` | `production_intake` \| `sale` \| `cut_in` \| `cut_out` \| `defect` \| `return` |
| `output_format`, `grade_code?`, `thickness_cm?` | что за товар |
| `qty` | со знаком: `+` приход, `−` расход |
| `ref` | текст-пояснение (номер партии производства / продажи / причина) |

`defect`/`return` заведены в справочнике статусов, но в текущем UI ручной кнопки для них
уже нет (была вкладка «Движение» на складе — её убрали по просьбе заказчика: списания/браки
сейчас происходят только неявно через продажу и нарезку). Если бэку нужен для отчётности —
оставить эндпоинт, фронт им пока не пользуется.

## 4. Касса → Продажи

```
GET  /api/foam/sales/
POST /api/foam/sales/
GET  /api/foam/sales/<id>/
```

`POST` body:

```json
{
  "client": "ИП Асанов",
  "sale_date": "2026-08-04",
  "lines": [
    { "key": "granule", "qty": "10", "unit_price": "50" }
  ],
  "paid_amount": "500"
}
```

Что делает бэк:

1. Для каждой строки найти остаток по `key`, `qty ≤ остаток` (иначе 400 с указанием
   доступного количества).
2. `total_amount = Σ(qty × unit_price)`.
3. `paid_amount` — клэмп в `[0, total_amount]`.
4. `debt_amount = total_amount − paid_amount`.
5. `payment_status`: `paid_amount == 0` → `debt`; `0 < paid_amount < total_amount` → `partial`;
   `paid_amount == total_amount` → `paid`.
6. Списать `qty` с каждой строки остатка склада ГП.
7. Записать операцию склада на каждую строку: `kind = sale`, `qty = −qty`, `ref = "Продажа {id}"`.
8. Сохранить продажу.

Поля продажи в ответе (для таблицы «Продажи», один в один с таблицей пластикового профиля):

| Поле | Тип |
|---|---|
| `id`, `date` | |
| `client` | см. открытый вопрос п.7.3 |
| `lines[]` | `output_format`, `grade_code?`, `thickness_cm?`, `qty`, `unit_price` |
| `total_amount`, `paid_amount`, `debt_amount` | |
| `payment_status` | `paid` \| `partial` \| `debt` |

«Тип продажи» в таблице — фронт сам формирует из `lines[].output_format` (перечисление
уникальных форматов через запятую), отдельного поля от бэка не нужно.

## 5. Права доступа

Никаких новых `access_key` заводить не планируем — линия пенопласта использует те же права,
что уже есть (`materials`, `production`, `warehouse`, `sales`). Если у заказчика в будущем
появится требование разграничить доступ по линиям отдельно (напр. кладовщик видит только
пенопласт) — тогда понадобится либо новый набор ключей, либо `line` как атрибут внутри
существующих прав. Сейчас в этом нет необходимости, фиксируем как открытый вопрос.

## 6. Формулы — обязательно совпадают 1:1 с фронтом

Сейчас все числа считает фронт (`src/features/foam/mockData.js`), после переезда на бэк
пересчёт должен давать **те же цифры**, иначе разъедутся склад/производство.

```
FOAM_CUBE_DIMS_CM   = { height: 60, width: 100, length: 200 }   // см, фиксировано всегда
FOAM_CUBE_VOLUME_M3 = 0.6 × 1.0 × 2.0 = 1.2                      // м³, фиксировано всегда
FOAM_PRODUCTION_LOSS_PERCENT = 3.5                                // %, технологические потери

usable_kg(input_kg) = input_kg × (1 − 0.035)

mid_density_kg_m3(grade) = (grade.min_kg_m3 + grade.max_kg_m3) / 2

cube_weight_kg(grade) = mid_density_kg_m3(grade) × 1.2

// Формат «Куб»: сколько кубов выйдет из загрузки (дробное значение — норм, льют по объёму)
output_qty_cube(grade, input_kg) = round(usable_kg(input_kg) / cube_weight_kg(grade), 1)

// Формат «Гранулы на продажу»: считается напрямую в кг, плотности нет
output_qty_granule(input_kg) = round(usable_kg(input_kg), 1)

// Нарезка куба на листы: сколько листов данной толщины из ОДНОГО куба
sheets_per_cube(thickness_cm) = floor(60 / thickness_cm)

// Вес одного листа
sheet_weight_kg(grade, thickness_cm) = mid_density_kg_m3(grade) × 1.0 × 2.0 × (thickness_cm / 100)

// Вес единицы остатка (для отображения кг на складе)
unit_weight_kg(row):
  cube    → cube_weight_kg(row.grade)
  sheet   → sheet_weight_kg(row.grade, row.thickness_cm)
  granule → 1   // единица остатка гранул уже кг
```

Округления везде — до **0.1** (кубы/кг), деньги — до **0.01**.

## 7. Открытые вопросы для бэкенда

1. **`lot_number`** — сейчас генерируется на фронте как `KG-{timestamp}` только для внутренней
   связки прихода с партией производства, пользователю не показывается (показывается
   `material_name`). На бэке это должен быть обычный автоинкремент/уникальный номер партии,
   формат — на усмотрение бэка, главное чтобы был стабильный `id` для связки.
2. **Права по линиям** — см. п.5, нужно ли разграничение, или общих `access_key` достаточно.
3. **Клиент в продаже** — сейчас это **свободный текст** (без выбора из справочника клиентов,
   без заявок/заказов, без накладных — сильно упрощённый чек-аут по сравнению с пластиковым
   профилем). Уточнить у продукта: оставить свободным текстом или связать с существующей
   моделью `Client` (`clients` app) как в пластиковой линии? Если связать — понадобится
   `client_id` вместо строки, и фронт нужно будет доработать (сейчас поле — обычный `<input>`).
4. **Способ оплаты (наличные/карта)** — в текущем прототипе продажи пенопласта это не
   учитывается (только статус «оплачено/частично/в долг» и сумма), в отличие от пластикового
   чек-аута с `payment_method`/`payment_splits`. Уточнить, нужен ли этот уровень детализации
   сразу или можно добавить позже.
