# Спецификация API зарплаты — расширение для неоплативших клиентов

## Текущий эндпоинт GET /api/salary/

Возвращает список расчётов по тренерам за период. Фронтенд ожидает для каждой строки:

### Требуемые поля в ответе (дополнительно к существующим)

| Поле (camelCase) | Тип | Описание |
|------------------|-----|----------|
| `totalClientCount` или `totalClients` | number | (опционально) Всего клиентов. Если нет — фронт считает paidCount + unpaidCount |
| `paidClientCount` или `clientCount` | number | Количество **оплативших** клиентов у тренера за период |
| `unpaidClientCount` | number | Количество **неоплативших** клиентов у тренера за период |

**Альтернативные имена** (фронт поддерживает): `unpaidCount`, `clientsUnpaid`, `unpaid` для неоплативших; `clientsCount`, `clients_count`, `count` для оплативших.

### Пример ответа

```json
{
  "items": [
    {
      "id": 1,
      "trainerId": 5,
      "trainerName": "Иванов Иван",
      "clientCount": 15,
      "unpaidClientCount": 2,
      "income": 30020,
      "trainerPercent": 60,
      "saved": false
    }
  ]
}
```

---

## Логика на фронте

- **Кнопка «Сохранить»** активна только когда:
  1. Месяц уже закончился (прошлый месяц)
  2. `unpaidClientCount === 0` (все клиенты оплатили)
  3. Запись ещё не сохранена (`saved === false`)

- Если `unpaidClientCount > 0` — кнопка неактивна, подсказка: «Сохранить можно только когда все клиенты оплатили».

---

## Рекомендация для бэкенда (опционально)

**POST /api/salary/save/** — при сохранении можно добавить проверку:

- Если у тренера за период есть неоплатившие клиенты → вернуть **400** или **409** с сообщением:
  ```json
  { "error": "Нельзя сохранить: у тренера есть неоплатившие клиенты" }
  ```

Это защитит от обхода проверки через API напрямую.

## КРИТИЧЕСКИЙ БАГ: Приход и аналитика меняются после сохранения зарплаты

### Проблема

1. Зарплата тренера за март сохранена (POST /api/salary/save/)
2. Приход, расход, аналитика показывают корректные данные
3. Пользователь удаляет клиента или меняет его статус «Оплачено»
4. **Приход пересчитывается** — сумма в аналитике меняется или пропадает (расход при этом может не меняться)

### Причина

Бэкенд при расчёте **прихода** и аналитики использует **текущее** состояние клиентов. Нет снимка данных на момент сохранения зарплаты.

### Требуемое исправление

**Если за период зарплата уже сохранена** — данные за этот период должны быть **заморожены** (snapshot):

1. **Приход** — сумма на момент сохранения, не пересчитывать при изменении/удалении клиентов
2. **Расход** (зарплата) — уже фиксируется при сохранении
3. **Клиенты, тренеры, оплачено/не оплачено** — все метрики аналитики за этот период берутся из снимка, а не из текущих данных

**Логика:** Раз зарплату сохранили — период «закрыт». Удаление или изменение клиента не должно влиять на приход, расход и аналитику за этот период.

## БАГ 2: Страница зарплаты (GET /api/salary/) тоже пересчитывается

### Проблема

Даже при закрытом периоде **страница «Зарплата»** (таблица с тренерами, доходом, оплатили/не оплатили) показывает данные из **текущих** клиентов. При изменении клиента — цифры в таблице меняются.

### Исправление

**GET /api/salary/** для закрытых периодов (есть PeriodSnapshot) должен возвращать данные **из снимка**, а не пересчитывать из клиентов.

В снимке должны быть: `salary_items` или аналог — строки по тренерам с income, clientCount, unpaidClientCount, saved и т.д.

## БАГ 3: 500 Internal Server Error при POST /api/salary/save/

### Проблема

При нажатии «Сохранить» за февраль (или другой месяц) сервер возвращает **500 Internal Server Error**.

### Что проверить на бэкенде

1. **Логи сервера** — посмотреть traceback, какая строка падает
2. **Создание PeriodSnapshot** — возможно, при первом сохранении падает создание снимка (нет поля, неверный тип, ошибка в JSON)
3. **Параметры запроса** — body: `trainerId`, `year`, `month`, `day`, `trainerPercent`. Проверить, что все обязательные поля приходят и обрабатываются
4. **Миграции** — применена ли миграция для PeriodSnapshot
5. **Связь с SalarySave** — не падает ли сохранение записи о выплате

**Действие:** Открыть логи Django (или другой бэк) при вызове POST /api/salary/save/ и по traceback найти причину 500.
