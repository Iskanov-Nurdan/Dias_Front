# DIAS ERP — UX-редизайн коммерческого контура (без изменения API)

## 1. Цель и рамки

Цель: перестроить UX фронтенда так, чтобы пользователь работал по бизнес-цепочке:

`Клиент -> Заявка -> Оплата -> Отгрузка -> Возврат -> Брак -> Переделка`

Принципы:
- backend и API не меняются;
- меняются только UI/UX, структура экранов, терминология, порядок действий;
- пользователь не видит технические поля и не работает в терминах API.

Не затрагивается:
- производство;
- складская логика FIFO и себестоимость;
- ОТК-поток;
- любые backend-контракты.

## 2. Информационная архитектура (новое верхнее меню)

Оставить в коммерческом контуре 5 главных вкладок:

1. `Заявки` (`/orders`)
2. `Отгрузки` (`/sales`)
3. `Оплаты` (`/payments`)
4. `Возвраты` (`/returns`)
5. `Брак и переделка` (единый UX над `/defects` + `/rework-requests`)

UX-правило: в этих разделах все тексты и элементы интерфейса должны быть бизнес-терминами, без внутренних идентификаторов.

## 3. Глобальные UX-стандарты для всех 5 вкладок

- Верхняя панель страницы:
  - заголовок;
  - быстрые фильтры;
  - кнопка основного действия (`Создать ...`);
  - поиск (где применимо).
- Основной контент:
  - таблица списка;
  - кликабельная строка открывает карточку (drawer/modal/page detail).
- Правая зона действий строки:
  - только бизнес-действия;
  - без технических команд.
- Карточка сущности:
  - раздел `Общее`;
  - раздел `Строки товаров`;
  - раздел `Связанные документы/операции`;
  - раздел `История`.
- Статусы всегда отображаются цветным `Badge`.
- Везде единая модель сообщений:
  - success-toast;
  - понятный текст ошибки;
  - пустые состояния без технических деталей.

## 4. Экран `Заявки` (`/orders`)

### 4.1 Список заявок

Колонки (в порядке):
1. `Номер`
2. `Дата`
3. `Клиент`
4. `Статус`
5. `Сумма`
6. `Оплачено`
7. `Осталось отгрузить`
8. `Действия`

Фильтры:
- период;
- клиент;
- статус.

Поиск:
- по номеру заявки;
- по названию клиента.

Действия строки:
- `Открыть`;
- `Редактировать`;
- `Сменить статус`;
- `Создать отгрузку`;
- `Принять оплату`;
- `Документы`.

### 4.2 Карточка заявки

Блоки:
- `Шапка`: номер, дата, клиент, статус, итог.
- `Товары`: таблица `Товар | Заказано | Отгружено | Остаток | Цена | Сумма`.
- `Связанные оплаты`: дата, тип, сумма, статус.
- `Связанные отгрузки`: номер отгрузки, дата, сумма, статус.
- `История изменений`: хронология бизнес-событий.

Кнопки:
- `Редактировать заявку`;
- `Создать отгрузку`;
- `Принять оплату`;
- `Скачать накладную заявки`.

### 4.3 Форма заявки

Минимальный состав полей:
- клиент;
- дата;
- строки товаров (товар, количество, цена);
- комментарий (опционально).

Скрыть из UI:
- `responsible_user_id`;
- любые технические поля строк.

## 5. Экран `Отгрузки` (`/sales`)

### 5.1 Ключевая UX-модель

- Одна отгрузка = документ с несколькими строками `SaleLine`.
- Полностью убрать визуальный паттерн `1 товар = 1 продажа`.

### 5.2 Список отгрузок

Колонки:
1. `Номер`
2. `Дата`
3. `Клиент`
4. `Статус`
5. `Сумма`
6. `Оплачено`
7. `Остаток`
8. `Действия`

Фильтры:
- период;
- клиент;
- статус;
- связанная заявка.

Действия:
- `Открыть`;
- `Редактировать`;
- `Создать из заявки`;
- `Частичная отгрузка`;
- `Документы` (накладная, квитанция).

### 5.3 Карточка/форма отгрузки

Блоки:
- шапка документа: клиент, связанная заявка, статус, дата;
- строки отгрузки: товар, количество, цена, сумма по строке;
- итоги: сумма, оплачено, остаток.

Ключевые UX-правила:
- пользователь редактирует только бизнес-поля;
- `order_line_id`, `warehouse_batch_id` и подобные внутренние поля скрыты за выборами с понятными названиями;
- частичная отгрузка оформляется как редактирование строк/количества без технических терминов.

## 6. Экран `Оплаты` (`/payments`)

### 6.1 Список оплат

Колонки:
1. `Дата`
2. `Клиент`
3. `Тип` (`Предоплата` / `Оплата` / `Возврат`)
4. `Способ`
5. `Сумма`
6. `Связанный документ`
7. `Действия`

Фильтры:
- период;
- клиент;
- тип оплаты.

### 6.2 Карточка клиента (финансы)

Показывать:
- `Оплачено`;
- `Выручка`;
- `Долг`;
- `Аванс`.

UX-правило:
- явно отделить оплату от продажи: платеж — отдельный финансовый документ, не "свойство продажи".

### 6.3 Форма оплаты

Поля:
- дата;
- клиент;
- тип оплаты;
- способ оплаты;
- сумма;
- привязка (заявка/отгрузка) — опционально;
- комментарий.

## 7. Экран `Возвраты` (`/returns`)

### 7.1 Список возвратов

Колонки:
1. `Номер`
2. `Дата`
3. `Продажа`
4. `Клиент`
5. `Причина`
6. `Статус`
7. `Действия`

### 7.2 Форма возврата

Блоки:
- шапка: продажа, дата, причина;
- строки возврата:
  - товар;
  - количество;
  - направление:
    - `На склад`;
    - `В брак`;
    - `На переделку`.

UX-правило:
- пользователь выбирает понятный маршрут возврата, а не технический `return_target`.

## 8. Экран `Брак и переделка` (единый UX на двух endpoint-группах)

Единый экран с 2 табами:
- `Брак` (данные `/defects`);
- `Переделка` (данные `/rework-requests`).

### 8.1 Таб `Брак`

Колонки:
1. `Продукт`
2. `Количество`
3. `Источник`
4. `Статус`
5. `Причина`
6. `Действия`

Действия:
- `Отправить на переработку`;
- `Продать брак`;
- `Списать`.

### 8.2 Таб `Переделка`

Колонки:
1. `Номер переделки`
2. `Продукт`
3. `Количество`
4. `Статус`
5. `Результат`
6. `Действия`

Действия:
- `Редактировать`;
- `Завершить переделку`.

## 9. Поля и данные, которые нельзя показывать пользователю

Запрещено выводить как пользовательские поля:
- `id` и внутренние PK в обычных таблицах;
- `order_line_id`, `sale_line_id`, `user_id`, `source_id`;
- `return_target` как технический код;
- технические связки backend и служебные атрибуты API.

Разрешено только:
- бизнес-названия;
- человекочитаемые номера документов;
- понятные статусы и суммы.

## 10. Статусы и цветовая модель

Единый шаблон:
- `Новый/Черновик` -> серый;
- `В работе/Подтверждено` -> синий;
- `Частично выполнено` -> оранжевый;
- `Завершено/Отгружено/Оплачено` -> зеленый;
- `Отменено/Списано` -> красный.

Требование:
- любой статус на списке и в карточке только через цветной `Badge` + русский label.

## 11. Документы

В UI явно выделить действия документов:
- для отгрузки: `Накладная`, `Квитанция`;
- для заявки: `Накладная заявки`;
- для возврата: `Акт возврата`.

Если backend не отдал файл:
- показать понятное сообщение;
- использовать существующий fallback (где уже реализован);
- не показывать технический текст ошибки.

## 12. Realtime/WebSocket (поведение UI)

Подписки коммерческого контура:
- `order`;
- `sale`;
- `payment`;
- `return`;
- `defect_record`;
- `rework_request`.

Поведение:
- при событии `change` по релевантному ресурсу -> `refetch` списка и карточки;
- если открыт документ/модалка и данные устарели -> показать ненавязчивый маркер "Данные обновлены";
- при token rejected/disconnect -> корректный выход и понятное уведомление.

## 13. Новый сквозной пользовательский сценарий

1. Менеджер создает клиента (или выбирает существующего).
2. Создает заявку и заполняет строки.
3. Регистрирует предоплату/оплату.
4. Создает отгрузку из заявки (возможна частичная).
5. Печатает накладную/квитанцию.
6. При необходимости оформляет возврат и выбирает маршрут.
7. Если возврат в брак: запись попадает в `Брак`.
8. При переделке: переводит в `Переделка`, завершает цикл.

## 14. Этапы дальнейшей реализации (после согласования UX)

1. Навигация и IA (5 коммерческих вкладок, единая терминология).
2. Пересборка списков/карточек `orders` и `sales` под документную модель.
3. Упрощение форм и скрытие технических полей.
4. Унификация статусов (badge + цвета).
5. Финальный UX-слой realtime и документов.

Этот документ является UX-целевой моделью перед кодовой реализацией.
