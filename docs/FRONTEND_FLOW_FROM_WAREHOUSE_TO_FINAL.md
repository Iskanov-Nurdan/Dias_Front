# FRONTEND FLOW: от «Склад» до финальных вкладок

Документ основан только на коде фронтенда (`src/app/routes/AppRoutes.jsx`, `src/shared/config/navigation.js`, `src/features/**`).

## 1) Склад

### 1. Маршрут и файлы
- `route`: `/warehouse`
- Главный компонент: `src/features/warehouse/components/WarehousePage/WarehousePage.jsx`
- Связанные файлы: `src/features/warehouse/components/warehouseBatchCard.js`, `src/features/warehouse/components/WarehousePage/WarehousePage.scss`
- Модалки: `ReserveModal`, `WarehouseBatchDetailModal`, `PackFromOtkModal`
- Hooks: `useServerQuery`, `useOperationalRefetch`, `useDiscardOnClose`, `useDirtyFromBaseline`
- API helpers:
  - `POST warehouse/batches/reserve/` (вызов прямо из страницы)
  - `packFromOtk` -> `POST warehouse/batches/package/` из `src/features/warehouse/api/warehouseApi.js`
  - `GET warehouse/batches/` (список и список партий для упаковки)

### 2. Что видит пользователь
- Таблица: продукт, статус, качество, физический остаток, резерв, свободно, партия.
- Фильтры: поиск (`input`), статус (`Select`), форма (`Select`), качество (`Select`).
- Кнопка `Упаковать` (desktop + mobile sticky).
- В строке: `ActionMenu` с действием `Резерв`.
- Badges: статус партии, форма инвентаря, качество.
- Empty state: `Нет партий`.
- Pagination: есть.
- Detail-окно: по клику на строку открывается карточка партии (`WarehouseBatchDetailModal`).

### 3. Что может сделать пользователь
- Открыть детали партии.
- Зарезервировать количество из доступной партии.
- Упаковать доступную `unpacked` партию.
- Работать с браком на складе:
  - в таблице видно `Качество=Брак` и причину брака;
  - резерв брака не запрещён (блокировка только по `status !== available`).

### 4. Формы и поля
- **Резерв (`ReserveModal`)**
  - `Продукт` (`input`, readonly, автоподстановка).
  - `Количество *` (`DecimalInput`, обязательно).
  - `№ продажи` (`input type=number`, необязательно, в `details`).
- **Упаковка (`PackFromOtkModal`)**
  - `Партия *` (`Select`, обязательно, список из API `available + unpacked`).
  - `Упаковок` (`IntegerInput`, обязательно, есть кнопка `Макс.`).
  - `Штук в каждой` (`IntegerInput`, обязательно).
  - `Комментарий` (`textarea`, необязательно).
  - Автоподстановка readonly-блока: качество, причина брака, геометрия, доступный остаток, списание, максимум по остатку.

### 5. UX/UI проблемы (по коду)
- В `ReserveModal` поле `№ продажи` — ручной ввод id, не выбор из списка.
- В `ReserveModal` для брака нет отдельного сценария/блокировки, пользователь может резервировать брак как обычную партию.
- В `PackFromOtkModal` сложная компоновка расчёта; для пользователя без контекста может быть неочевидно, что списание = `упаковки × штук`.
- В `ActionMenu` только один пункт `Резерв`; для строки без доступных действий меню остаётся, но с disable.

### 6. Что уже совпадает с backend
- Фильтрация списка отправляется параметрами (`status`, `search`, `inventory_form`, `quality`).
- Резерв отправляет числовой payload: `batch_id`, `quantity`, опционально `sale_id`.
- Упаковка отправляет поля, которые ожидает API: `warehouse_batch_id`/`warehouse_batch`, `pieces_per_package`, `packages_count`, `comment`.

### 7. Что не совпадает/рисково по контракту
- Фронт отправляет **оба** поля `warehouse_batch_id` и `warehouse_batch` в упаковке (явный признак адаптации к разным контрактам).
- В разных местах используются альтернативные ключи ответа (`batch|lot`, `product_name|product`), значит фронт уже учитывает неоднородный ответ API.

### 8. Что нельзя показывать пользователю
- `sale_id` как ручной технический id в резерве.
- Технические коды статусов/форм/качеств (в UI они уже обёрнуты в label/badge).

## 2) Клиенты

### 1. Маршрут и файлы
- `route`: `/clients`
- Главный компонент: `src/features/clients/components/ClientsPage/ClientsPage.jsx`
- Модалки: `ClientModal`, `ClientDetailModal`, `HistoryModal`, `ConfirmModal` удаления

- API: `GET/POST/PATCH/DELETE clients/`, `GET clients/{id}/history/`, `GET payments/summary/`, fallback `GET sales/`

### 2. Что видит пользователь
- Таблица: клиент, телефон, контакт, число продаж, сумма, статус.
- Поиск + кнопка `Создать`.
- `ActionMenu`: открыть, редактировать, история, удалить (если нет продаж).
- Карточка клиента (detail): основные данные + связанные данные.
- История: события + финансовая сводка.
- Empty state: `Нет клиентов`.
- Pagination: есть.

### 3. Что может сделать пользователь
- Создать клиента.
- Редактировать клиента.
- Удалить клиента без продаж.
- Открыть карточку клиента.
- Открыть историю и финансовый блок.

### 4. Формы и поля
- **ClientModal**
  - `Название / компания *` (`input`, обязательно).
  - `Контактное лицо` (`input`).
  - `Телефон` (`input`).
  - `WhatsApp / Telegram` (`input`).
  - `Email` (`input type=email`).
  - `Клиент активен` (`checkbox`).
  - В `Collapse "Ещё"`: `Доп. телефон`, `Адрес`, `Тип`, `Комментарий`.
  - Автологика payload: в зависимости от структуры объекта клиента отправляется `messenger` или `whatsapp_telegram`.

### 5. UX/UI проблемы
- Поле `Тип` — свободный `input`, нет словаря/`Select`.
- В карточке и таблице видны агрегаты, но без расшифровки источника расчёта.
- История зависит от нескольких API; при частичных ошибках данные могут быть неполными без явной причины в UI.

### 6. Что уже совпадает с backend
- Фронт поддерживает оба набора полей: `phone|phone_number`, `contact_person|contact_name`, `name|title`, `notes|comment`, `is_active|active`.
- Финсводка использует `payments/summary/` и отображает кредитные поля, если сервер их вернул.

### 7. Что не совпадает/рисково по контракту
- История клиента имеет fallback через `sales/` при пустом `clients/{id}/history/`, значит контракт истории не стабилен.

### 8. Что нельзя показывать пользователю
- Сырые id клиента и технические названия fallback-полей.

- Фильтры: поиск + статус.

- Empty state: `Нет заявок`.

### 3. Что может сделать пользователь

  - `Комментарий` (`textarea`)
  - Строки заявки:

  - `Клиент` (readonly)

- **AcceptPaymentModal**
  - `Дата`, `Клиент` readonly
  - `Тип оплаты` (`Select`)
  - `Способ оплаты` (`Select`)
  - `Сумма` (`input`, обязательно)

### 5. UX/UI проблемы
- В строках заявки `Товар` и `Тип товара` — свободные `input`, нет выбора из справочников.
- Нет единой пошаговой формы: create/edit + отгрузка + оплата разбросаны по разным модалкам.
- В `OrderModal` нет отдельной detail-логики для строк при редактировании: сразу форма.

### 6. Что уже совпадает с backend
- Статусы и allowed transitions зафиксированы в фронте.
- Резервы читаются отдельным endpoint `orders/{id}/reservations/`.
- Накладная поддерживает бинарные ответы и JSON-ошибки.

### 7. Что не совпадает/рисково по контракту
- Для расчёта `remaining_to_ship` фронт содержит fallback-формулу по строкам (признак, что поле не всегда приходит).
- В ответах используются альтернативные структуры списков (`results|items|array`).

### 8. Что нельзя показывать пользователю
- `linked_order`, `order_line`, прочие служебные id как ручной ввод (сейчас в UI это скрыто за Select/readonly).

## 4) Продажи

### 1. Маршрут и файлы
- `route`: `/sales`
- Главный компонент: `src/features/sales/components/SalesPage/SalesPage.jsx`
- Связанные: `WaybillPreviewModal.jsx`, `src/features/sales/api/salesApi.js`
- Модалки: `SaleModal`, `WaybillPreviewModal`, удаления, credit override confirm
- Hooks: `useServerQuery`, `useOperationalRefetch`, `useAuth`
- Документы:
  - preview/печать накладной в модалке
  - `downloadSaleWaybill` (серверные endpoint + локальный fallback draft html)
  - `downloadSaleReceipt`

### 2. Что видит пользователь
- Таблица: дата, клиент, номер, заявка, статус, выручка, оплачено.
- Фильтры: статус, клиент, диапазон дат.
- `ActionMenu`: редактировать, накладная, квитанция, смена статуса, удалить.
- Empty state: `Нет продаж`.
- Pagination: есть.

### 3. Что может сделать пользователь
- Создать продажу.
- Редактировать мета-поля продажи (не строки).
- Переводить статус по allowed transitions.
- Скачать/печатать накладную, скачать квитанцию.
- Удалить продажу.
- Выполнить `force_credit_override` через confirm-модалку, если у пользователя есть права.

### 4. Формы и поля
- **SaleModal (create)**
  - `Дата продажи` (`date`)
  - `Клиент` (`Select`)
  - `Связанная заявка` (`Select`)
  - `Комментарий` (`textarea`)
  - Строки:
    - `Товар *` (`input`)
    - `Партия склада` (`Select`)
    - `Количество *` (`input type=number`)
    - `Цена` (`input type=number`)
    - `Комментарий` (`input`)
- **SaleModal (edit)**
  - Строки и партия недоступны для изменения (явно указано в UI).
- **WaybillPreviewModal**
  - Только просмотр двух копий, кнопки `Скачать`, `Печать`.

### 5. UX/UI проблемы
- При создании `Товар` — ручной `input`, даже при выборе партии.
- При редактировании нельзя править строки: ограничение есть, но пользователь узнаёт об этом только внутри модалки.
- Кредитный override реализован confirm-диалогом без отдельного explain-экрана (контекст причины минимальный).

### 6. Что уже совпадает с backend
- Статус меняется отдельным endpoint `sales/{id}/status/`.
- Для превышения лимита отправляется `force_credit_override`.
- Документы обрабатывают разные типы ответов (pdf/html/xlsx/json-error).

### 7. Что не совпадает/рисково по контракту
- Для накладной фронт пробует сразу 3 endpoint (`nakladnaya`, `waybill`, `invoice`) и при неуспехе генерирует локальный draft HTML — явный признак отсутствия единого стабильного endpoint.

### 8. Что нельзя показывать пользователю
- Технические признаки fallback (`source: local`, служебные коды ошибок лимита).
- Сырые id продаж в подписях вида `#id` (сейчас используются как fallback в UI).

- Создать/редактировать возврат.

  - `Продажа *` (`Select`, обязательно)

    - при выборе строки продажи заполняется `product`;
    - количество ограничивается `cap`, если API отдал верхнюю границу.

- Валидация лимита количества частично фронтовая, частично серверная, это видно по сообщениям.

### 6. Что уже совпадает с backend
- Используются backend-роуты маршрутизации в брак/переделку через `return_target`.
- Поддерживаются серверные поля лимита возврата с несколькими именами (`returnable_quantity`, `remaining_return_quantity`, и т.д.).

### 7. Что не совпадает/рисково по контракту
- Фронт вынужден поддерживать набор альтернативных полей по лимиту строк и по структуре продажи (`sale_lines|lines`), что указывает на неунифицированный контракт.

### 8. Что нельзя показывать пользователю
- `sale_line` id и технические внутренние ключи лимита.

  - `Комментарий` (`textarea`)
- **Завершение переделки**
  - `Результирующая партия *` (`Select`, обязательно)

### 5. UX/UI проблемы
- Главный сценарий пользователя разбит на много `ConfirmModal`; нет единого detail-потока.
- Критичные поля (`Продукт`, `Цена`, `Количество`) во многих шагах — ручные `input`, не выбор из нормализованных сущностей.
- В `Брак` и `Переделка` нет отдельной полноэкранной карточки; действия сразу из action menu.
- Для завершения переделки модалка требует выбрать партию, но не показывает детально контекст результата (только short label).

### 6. Что уже совпадает с backend
- Экшены вынесены в отдельные backend endpoint (`send-to-rework`, `complete-rework`, `writeoff`, `sell`, `start`, `complete`, `cancel`).
- Действия жёстко ограничены статусом на фронте.

### 7. Что не совпадает/рисково по контракту
- Фронт использует множественные стратегии чтения id (`*_id`, nested object, number/string), это адаптация к разнородным ответам API.
- Для завершения переделки отправляется `result_warehouse_batch_id`; без него фронт блокирует submit.

### 8. Что нельзя показывать пользователю
- Технические id связанных сущностей (`defect_record_id`, `return_doc_id`, `original_sale_id`, `result_warehouse_batch_id`) как raw-поля ввода.

## 10) WebSocket / синхронизация для этих разделов

### Как устроено
- Провайдер: `OperationalRealtimeProvider` подключает один канал `/ws/operational/?token=...`.
- Активируется только при авторизованном пользователе и наличии `token`.
- Обрабатывается только событие `event === "change"` с полем `resource`.
- Хук `useOperationalRefetch(resources, refetch)` вызывает `refetch()` при совпадении `resource`.

### Где покрыто
- `Склад`: `warehouse_batch`, `production_batch`, `batch`
- `Клиенты`: `sale`, `payment`, `order`
- `Заявки`: `order`, `sale`, `payment`, `return`
- `Продажи`: `sale`, `warehouse_batch`, `order`, `payment`, `return`
- `Оплаты`: `payment`, `sale`, `order`, `return`
- `Возвраты`: `return`, `defect_record`, `rework_request`, `sale`
- `Брак`: `defect_record`, `sale`, `rework_request`
- `Переделка`: `rework_request`, `defect_record`, `warehouse_batch`
- `Аналитика`: WS-refetch не подключён (страница обновляется только через фильтры/перезагрузку)

### Где возможен рассинхрон
- При изменениях в аналитике по данным операционных модулей, т.к. нет `useOperationalRefetch`.
- Если backend отправляет `resource`, не включённый в ресурс-лист страницы, автообновления не будет.

## 1. Что уже сделано хорошо
- Во всех целевых коммерческих вкладках есть таблица, empty state, обработка загрузки/ошибки, pagination.
- Для большинства действий используются явные статусные ограничения (кнопки/пункты menu отключаются по бизнес-статусу).
- Документы скачиваются с защитой от невалидного blob/JSON-ошибок.
- WebSocket-синхронизация централизована и подключена почти ко всем операционным разделам.

## 2. Что ещё реально неудобно
- Много ручных `input` там, где сущность уже существует в системе (`товар`, `тип`, `№ продажи`, `цены/количества` в ряде сценариев).
- Во многих местах нет отдельного detail-экрана: пользователь попадает сразу в редактирование или confirm-диалог.
- Сценарии брака/переделки/возврата фрагментированы между несколькими модалками без единой пошаговой навигации.
- Для документов UX неоднородный: где-то preview+печать, где-то только скачивание.

## 3. Что является ошибкой фронта
- В `Склад -> Резерв` поле `№ продажи` реализовано как ручной ввод id вместо выбора.
- В `Склад` нет фронтового запрета резервировать брак (если статус `available`, пункт `Резерв` доступен).
- В аналитике нет realtime-подписки, тогда как операционные данные обновляются через WS в других разделах.

## 4. Что является проблемой backend-контракта (по фактам из кода)
- Для накладной продажи фронт вынужден пробовать три разных endpoint и иметь локальный fallback-документ.
- Во многих разделах фронт обрабатывает альтернативные названия одинаковых полей (`*_id`, nested object, разные ключи метрик/остатков/лимитов), что указывает на неоднородный ответ API.
- В истории клиента фронт делает fallback через `sales/`, если `clients/{id}/history/` не возвращает ожидаемые строки.
